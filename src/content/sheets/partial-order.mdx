## Three stations do not make one log

An operator at station A records a signal report. A sends a copy to station B.
An operator at C records a separate report without exchanging messages with
A or B. B then receives A's message.

B can learn about A's report from that delivery. It cannot learn about C's
report. Yet if you list events in the order you clicked the lab controls,
C's report appears before B's receive. Does that mean B could use it?

No. Button order records your actions, not what each station knows.
As in [Local history](/atlas/local-history/), each station represents a
computer with its own record. The stations learn about other stations'
events through messages.

A **partial order** records which events must come before others while
leaving some pairs unordered. Here, A's report must come before B receives
it. The exchange gives no order between C's report and B's receive.
Leaving that pair unordered preserves the difference between an earlier
button click and information available at a station.

## Read edges as dependencies

The lab gives the events short names: `a1` is A's report, `b1` is B's
receive, and `c1` is C's report. It also records arrows between events.
An arrow, or **edge**, points from an earlier event to one that follows it.
A **path** is one or more arrows followed in their direction.

Two kinds of connection matter: the order of events at one station, and
the connection from sending a message to receiving it. Together, these
connections describe how information could pass between events.

The <dfn><a href="/glossary/#happens-before">happens-before</a></dfn>
relation describes this order. It follows three rules:

1. At one station, an earlier event happens before a later event.
2. Sending a message happens before receiving that message.
3. If `x` happens before `y`, and `y` happens before `z`, then `x` happens
   before `z`. This rule is called **transitivity**: you can follow a path
   through intermediate events.

<TermCallout
  term="happens-before"
  definition="The strict relation generated by local event order, message send-to-receive order, and transitivity."
  inlineOnly
/>

For this lesson, the lab records sending as an action without giving it a
separate event name. It shows `a1 -> b1` because A recorded `a1`, then sent
the message that B received. This is the same simplification used in
Local history. Sending is still an event in the full happens-before model.

A path shows that information could have passed between events. It does not
prove that an application used that information. For example, B might receive
A's report and then perform an unrelated calculation. The receive still
happens before that later local event.

## Compare the connected and disconnected pairs

Use the **Guided run** and its **Next:** button for all five steps. Choose
**Reset lab** first if you have already used other controls.

1. Record `a1` at A.
2. Send `m1` from A to B. B has not received anything yet.
3. Record `c1` at C. C sends no message.
4. Deliver `m1`. B records the receive as `b1` and learns about `a1`.
5. Compare `a1 / b1`, `b1 / c1`, and `c1 / c1`.

Before the fifth step, predict the results. Which pair has a path? Which
pair has none? Which pair names the same event twice?

## A missing path is a result

After delivery, the message provides a path from `a1` to `b1`.
Nothing in that message mentions `c1`, and C has received nothing from B.
There is no path between `b1` and `c1` in either direction.

These two distinct events are
<dfn><a href="/glossary/#concurrency">concurrent</a></dfn>. Here, concurrency
means that neither event happens before the other. It does not mean that
they occurred at the same instant. You clicked C's event first, but no
message connected it to B's receive.

  strict happens-before never relates an event to itself.</figcaption>

The interface distinguishes **equal** from **concurrent**. Equal means
the same event, not two events with the same value or time. Concurrent means
two different events with no path between them.

Happens-before is a **strict** partial order: an event never happens before
itself. If you also include equality, you get the corresponding non-strict
partial order. The interface reports equality separately so you can tell
event identity from event order.

To try transitivity, choose **Send from B to C** after the guided run and
deliver the new message. B's message includes what B learned about `a1`.
The new receive at C follows `b1`, which follows `a1`. It therefore follows
`a1` even though A sent no message directly to C.

C's earlier event `c1` remains concurrent with `b1`. Receiving information
later does not change what was available to an earlier event.

## Break it: sort the buttons

Suppose you add an arrow from `c1` to `b1` because you clicked C's control
first. That arrow would claim a path that the execution does not contain.
B received only A's message.

You can still choose a single sequence for display. A **total order** places
every pair of distinct events in an order. All three sequences below
respect the one required connection, `a1 -> b1`:

- `a1, c1, b1`
- `c1, a1, b1`
- `a1, b1, c1`

Choosing one sequence does not change the partial order. Before claiming
that one event happens before another, find a path through local event
order and message delivery. A display position alone is not evidence.

</section>

<section class="sheet-costs" aria-labelledby="what-a-path-check-assumes">

## What a path check assumes

The lab keeps an event graph: the events and arrows connecting them.
Keeping more events requires more storage. Following long paths can also
take more work than checking a direct connection.

The lab records every event and message in this simulated run. Real logs
may be incomplete. A missing message record does not prove that no message
was sent. Only call events concurrent when you have enough information to
rule out a path in either direction.

You can inspect all three stations, but each station still has only its
own observations. The full view is a teaching tool, not information that
every station automatically shares.

</section>

<section class="sheet-field-notes" aria-labelledby="field-notes">

## Field notes

Use these rules when comparing two events:

```text
Same event?                  equal
Path from first to second?   before
Path from second to first?   after
Different events, no path?   concurrent
```

Check identity first. Follow arrows only in their direction. Two events
that share an earlier event are not necessarily ordered relative to each
other: both may follow that event without a path between them.

Lamport's
[Time, Clocks, and the Ordering of Events in a Distributed System](/bibliography/#lamport-time-clocks)
defines happens-before and shows how to extend it to a total order.
The distinction in this lesson is the same: an order chosen for display
does not create communication between events.

Read [Local history](/atlas/local-history/) if the difference between execution
and observation is unclear. Read [Lamport clocks](/atlas/lamport-clocks/)
to see how a station can assign a number to each event while preserving
happens-before order.

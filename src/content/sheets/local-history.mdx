## A delayed message can contain old news

An operator at station A writes a draft signal report and sends a copy to
station B. The message takes time to arrive. Before it reaches B, the
operator at A publishes the report.

B receives the draft. It has no news of the published report.
Receiving a message does not mean having the latest information.

Two computers that keep copies of a document can have the same problem.
One can change its copy while a message is on the way. The copies can differ
even if no message is lost.

Each station in this lesson stands for a computer with a copy of the report.
We call each computer a **replica**. The lab lets you see both stations,
but neither station can read the other's panel.

## Separate what happened from what is known

A <dfn><a href="/glossary/#local-history">local history</a></dfn> is an ordered
record of events at one station. An **event** is an action there, such as
writing a draft or receiving a message.

<TermCallout
  term="local history"
  definition="The ordered events executed at one replica."
  inlineOnly
/>

The lab uses short names for these events:

- `a1`: A writes the draft.
- `a2`: A publishes the report.
- `b1`: B receives the message.

A records `a1` before `a2`. B records `b1`, because B received the draft.
B did not write it.

An <dfn><a href="/glossary/#observation">observation</a></dfn> is information
that a station has from its own events or messages it receives.

<TermCallout
  term="observation"
  definition="Information available to a replica through its own events and received messages."
  inlineOnly
/>

After delivery, compare B's two fields:

- **Local history** lists `b1`. This answers "What happened here?"
- **Observed events** lists `a1` and `b1`. This answers "Which events does
  B know about?"

In this lab, a station sends a copy of the events it knows about. The receiver
adds those events to **Observed events** and records its own receive event.

The lab records the send action without a separate event name.
A's **Local history** still lists only `a1` after the send. This keeps the
example small. Sending can count as an event in other models.

## Hold the message while A changes

Use **Guided run** and its **Next:** button for these four steps.
Choose **Reset lab** first if you have used other controls.

1. Record the draft at A. A's local history and observed events both contain
   `a1`. B's records are still empty.
2. Send from A to B. Find `m1` in **Queued messages**, where messages wait
   for delivery. It contains `a1`. B has not received it.
3. Record publication at A. A now lists `a1, a2`. Inspect `m1` again:
   it must still contain only `a1`.
4. Deliver `m1`. B records `b1`. Compare **Local history** and **Observed
   events** at each station.

Use **Next:** to get the event names in this example. The separate delivery
button gives the receive event a different name instead of `b1`.

Before step 4, predict whether B will learn that A published the report.
After delivery, check B's records as well as the queue.

Without JavaScript, the lab shows empty starting records. You can follow the
example in the figures above and below without using the controls.

## Check what B knows

B learns nothing from `m1` until it arrives. When A publishes the report,
A's record changes. The copy in `m1` stays the same.

After delivery, B knows about the draft (`a1`) and its own receive (`b1`).
It has no record of A publishing the report (`a2`).

An empty queue does not mean both stations have the same information.
You delivered the earlier copy. B sends no reply in this run, so A does not
know that B received it.

To tell B about `a2`, choose **Send from A to B** after the guided run.
Deliver the new message. B learns that A published the report and records
a new receive event. The first receive event stays in B's history.

<section class="sheet-break" aria-labelledby="break-it-read-the-sender-at-delivery">

## Break it: read the sender at delivery

Suppose the lab read A's current record when you delivered `m1`.
B would learn about both the draft and the published report.
That would be wrong: A sent `m1` before publishing.

Check `m1` at steps 2 and 3. It must still contain only `a1` after A changes.
Then check B after step 4. B should have no record of `a2`.
The delivery worked; the message had no news of that event.

<section class="sheet-costs" aria-labelledby="the-cost-of-an-explicit-history">

## The cost of an explicit history

The lab names events so you can check what each station knows.
Longer runs need more space for records and larger messages.
Real applications do not have to send their full history in each message.

You control when messages arrive. Sending a message does not guarantee
that it arrives. A delay is enough to leave B with an old record;
the network does not have to fail.

</section>

## Field notes

Use this short record to check the result:

```text
A records draft a1.
A sends m1 containing a1.
A records publication a2.
B receives m1 as b1 and learns about a1.
B has not learned about a2.
```

A local history records what happened at one station. Observations also
include events learned from messages. B can learn what A sent in a message,
but it cannot use that message to learn about A's later changes.

For further reading, Leslie Lamport's
[Time, Clocks, and the Ordering of Events in a Distributed System](/bibliography/#lamport-time-clocks)
explains how events and messages set the order of events across computers.
You do not need those formal rules for this lesson.

The lab also shows an event comparison. You can leave that aside here.
[Partial order](/atlas/partial-order/) explains those comparisons in the
next lesson.

## A delayed message can contain old news

Station A records a draft signal report and sends a copy to station B. While
the network delays delivery, an operator at A publishes the report. B then
receives the earlier message. Does B know that the report was published?

No. The message contains the record that A sent, not A's later changes.
B learns about the draft, but not about publication. A delivered message does
not mean that the receiver is up to date.

The same problem can occur when two computers keep copies of a document.
One computer can change its copy while a message is still on its way to the
other. No message needs to be lost for the copies to differ.

In this lesson, each station represents a computer that keeps its own copy
of the report. Such a computer is called a replica. You will compare what
happened at each station with what it learned from a message.
The lab shows both stations so you can see the difference. Neither station
can read the other station's panel.

## Keep execution and observation separate

A <dfn><a href="/glossary/#local-history">local history</a></dfn> is an ordered
record of events at one station. An event is something that happens there,
such as recording a draft or receiving a message.

<TermCallout
  term="local history"
  definition="The ordered events executed at one replica."
  inlineOnly
/>

The lab gives each event a short name. `a1` is A's draft event, and `a2` is
A's publish event. A records them in that order. B's receive event is `b1`.
Receiving information about A's draft does not mean that B created the draft.

An <dfn><a href="/glossary/#observation">observation</a></dfn> is information
available at a station, either from its own events or from received messages.

<TermCallout
  term="observation"
  definition="Information available to a replica through its own events and received messages."
  inlineOnly
/>

After delivery, B's **Local history** lists `b1`: B received a message.
Its **Observed events** lists `a1` and `b1`: B also learned about A's draft.
Use the first field to ask "What happened here?" Use the second to ask
"Which events does this station know about?"

For this experiment, sending copies the station's observed events into a
message. Delivery adds that information at the receiver and records a receive
event there.

The lab records sending as an action, but does not give it a separate event
name in this lesson. A's local history therefore still lists only `a1` just
after the send. This is a teaching simplification, not a rule that sending
cannot be an event.

## Hold the message while A changes

Use the **Guided run** and its **Next:** button for all four steps. If you
have already used other controls, choose **Reset lab** first.

1. Record the draft at A. A's local history and observed events both contain
   `a1`. B's records are still empty.
2. Send from A to B. Find `m1` in **Queued messages**, the list of messages
   waiting for delivery. It contains `a1`. B has not received it yet.
3. Record publication at A. A now lists `a1, a2`. Inspect `m1` again:
   it must still contain only `a1`.
4. Deliver `m1`. B records `b1`. Compare **Local history** and **Observed
   events** at each station.

The guided buttons supply the event names used here. The separate delivery
button uses a generated name instead of `b1`, so use **Next:** to match
the example.

Before the last step, predict whether B will learn about publication.
After delivery, check B's records rather than just checking that the message
has left the queue.

Without JavaScript, the lab shows the empty starting records. The figures
above and below provide the example's message contents and final records
without requiring the controls.

## Account for the missing event

Sending does not change B's records. The information is waiting in `m1`,
and B cannot use it until delivery.

Publication changes A's record, but not the copy already in `m1`.
After delivery, B knows about the draft and its own receive event. It has no
record of publication.

An empty queue does not mean both stations have the same information.
All you delivered was the earlier copy. Also, A has not learned that B
received it: this run includes no reply from B.

To tell B about `a2`, choose **Send from A to B** after the guided run,
then deliver the new message. B learns about publication and records another
receive. The first receive still describes the first delivery.

<section class="sheet-break" aria-labelledby="break-it-read-the-sender-at-delivery">

## Break it: read the sender at delivery

Suppose the lab read A's current record at delivery instead of using the
saved message. B would learn about both the draft and publication from `m1`.
That would be wrong: A sent `m1` before publication.

Check the message at steps 2 and 3. Its contents must remain `a1` even as A
changes. Then check B after step 4. The absence of `a2` is the expected
result, not a delivery failure.

</section>

<section class="sheet-costs" aria-labelledby="the-cost-of-an-explicit-history">

## The cost of an explicit history

The lab keeps named events so you can inspect exactly what each station has
observed. Longer runs need more space to store these records and send copies.
A real application need not include its entire history in every message.

You also control when delivery happens. Sending alone does not guarantee
receipt. This example uses one delayed message to show the difference; you
do not need a network failure to produce an out-of-date record at B.

</section>

<section class="sheet-field-notes" aria-labelledby="field-notes">

## Field notes

Use this short record to check the result:

```text
A records draft a1.
A sends m1 containing a1.
A records publication a2.
B receives m1 as b1 and learns about a1.
B has not learned about a2.
```

The distinction to keep is simple: a local history records what happened
at one station. An observation can also include information received from
another station. A message tells the receiver what was sent, not everything
that happened afterward.

For further reading, Leslie Lamport's
[Time, Clocks, and the Ordering of Events in a Distributed System](/bibliography/#lamport-time-clocks)
explains how local events and messages establish order in a distributed
system. You do not need its formal rules for this lesson.

The lab also shows an event comparison. You can leave that aside here.
[Partial order](/atlas/partial-order/) explains those comparisons in the
next lesson.
